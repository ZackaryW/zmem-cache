# Adaptive comparison

`python benchmarks/tiered_history.py --adaptive-workload --service target/adaptive/debug/zmem-svc.exe --lookup-clients 1 --warm-samples 30 --repetitions 3 --output benchmarks/results/adaptive-1.json`

Repeat with `--lookup-clients 8`, and with the frozen corrected predecessor at `target/corrected-predecessor/zmem-svc.exe`. Run measurements serially without a simultaneous test suite. The workload uses three 1600-commit merged, annotation-bearing repositories: once-used, repeatedly shallow, and progressively deeper. It sets a 450000-byte staging quota, uses an installed host, overlaps timed warm lookups with a deep check, and measures an explicit 1000-to-1500 depth increase. It asserts zero shallow-triggered speculation, exactly 500 produced/reused adaptive facts, and unchanged cross-window CANCEL and META behavior.

The eligible adaptive route is a **controlled persisted-demand fixture** representing two previous 1000-commit observations 60 seconds apart. The benchmark does not speed up the daemon's clock or shorten process deadlines. Promotion interval/expiry behavior is covered separately by controlled-clock policy tests; these measurements compare collection, utilization and foreground latency once that prior demand exists. Both binaries stop/restart outside the timed warm phase. Each JSON result includes binary SHA-256, sample count, p50/p95/p99, within-run population standard deviation, cold/wider latency, and remaining unused bytes. Schema-5 predecessor utilization counters are unavailable; its unused raw facts/edges are measured directly using the same retained-membership predicate. For exact predecessor production/reuse counts, run a separate `--utilization-audit --repetitions 1 --warm-samples 1` pass: it settles and enumerates each completed cohort before the next repository can reclaim it. Audit timings are excluded from the matched latency comparison because that setup adds explicit checkpoint waits.

The original script mode below describes the predecessor's eager behavior; use `--service target/corrected-predecessor/zmem-svc.exe` for those historical exercises. Adaptive promotion does not promise the old unconditional 10000-fact endpoint.

# Tiered history measurement

Run `python benchmarks/tiered_history.py --commits 10000 --warm-samples 30` after building `target/debug/zmem-svc` and installing the adjacent Python extension host. The script creates a disposable linear Git history and isolated `ZMEM_HOME`, admits a one-commit requested trail, waits for publication, measures repeated exact-HEAD queries, then checks that raw-fact prefetch reaches the configured ceiling. It uses a single SQLite database and stops the daemon before deleting the home. Add `--trace-git` for Git process counts; trace I/O changes the timing and should be measured separately.

Add `--merge-every 50` for a graph with a side commit and merge about every 50 commits. On Windows, 2026-09-26, the 10,000-commit merged run stored 10,198 raw parent edges and zero transitive ancestor rows. All 30 warm samples overlapped backfill: p50 192.0 ms, p95 217.4 ms, p99 221.5 ms. The requested trail published in 463.8 ms, raw-fact prefetch finished about 16.1 seconds later, and the database file was 4,886,528 bytes. A separate linear run stored 9,999 raw parent edges and zero transitive ancestor rows. Both are linear in the number of commits plus merge edges and below the provisional 250 ms warm-p95 target for these isolated runs.

Add `--deep-check` to overlap a 500-commit deep check with warm queries. A 10,000-commit merged run using `--merge-every 50 --deep-check` had all 30 warm samples overlap both the check and backfill: p50 206.2 ms, p95 224.7 ms, p99 225.1 ms. The deep check completed in 12,884.6 ms. The requested trail published in 532.7 ms, and the graph again had 10,198 raw parent edges and no transitive ancestor rows. This check used a proposed `zmem(DECISION)` message and did not publish hypothetical results.

Use `--installed-host --trace-host` to run with a disposable installed Python host and count identity operations. On Windows, 2026-09-26, a 10,000-commit merged run had zero identity-host calls during 30 warm lookups overlapping backfill: p50 110.0 ms, p95 126.8 ms, p99 129.6 ms. A run also overlapping a deep check had p50 126.0 ms, p95 148.5 ms, p99 160.7 ms; the one identity call during that interval belonged to the deep check. Both runs stored 10,198 parent edges and zero transitive ancestor rows. The host trace changes timing, so these are separate samples from the earlier development-host runs.

The benchmark now samples job-status queue depth and the SQLite WAL file while work runs. In a subsequent 10,000-commit installed-host merged/check run, requested work waited 8 ms in the job queue and ran 412 ms; the observed queue-depth peak was zero because the single requested job had already been dequeued when polling began. WAL size was 4,152 bytes when the requested trail became ready and reached an observed 4,548,512-byte peak during backfill. All 30 warm samples overlapped the 10.5-second deep check and backfill at p50 120.7 ms, p95 138.6 ms, p99 140.6 ms. These are sampled WAL/queue observations, not transaction-duration or maximum-concurrency measurements.

`--trace-host` also records process start/end events in separate per-process files, avoiding concurrent append interleaving. In a fresh 10,000-commit merged/check run after batch rotation, the observed peak was three simultaneous host processes, with no unmatched starts or malformed events. Warm p50/p95/p99 was 123.1/139.0/139.7 ms while all 30 lookups overlapped deep check and backfill; requested queue wait/work were 9/435 ms and observed WAL peak was 4,548,512 bytes. This is a one-check workload, below the configured eight-host ceiling, rather than a saturation test.

Use `--requested-commits 500` to measure the default recent tier instead of the one-commit smoke trail. With 10,000 merged commits, one warm lookup client and a concurrent deep check, the 500-commit indexing job took 10,708 ms and its writer-owned publication transaction took 24,588 microseconds. The WAL file grew from 94,792 to 972,352 bytes across that transaction. Thirty warm lookups all overlapped deep check and backfill at p50 124.3 ms, p95 141.6 ms, p99 154.9 ms; host peak was four, and the database file finished at 5,591,040 bytes. The host trace had no unmatched starts or malformed events. `--lookup-clients 8` repeats the 30 samples in concurrent batches; under the same merged/check/backfill load, p50/p95/p99 rose to 246.3/459.8/460.6 ms and host peak to five. Thus the provisional 250 ms warm-p95 target passed for one client but not eight simultaneous clients on this machine; the two reserved lookup workers bound throughput and queueing adds latency.

After routing retention and branch-alias updates through the writer, repeat runs of that 10,000-commit merged/check/backfill case measured one-client p50/p95/p99 at 126.7/147.8/150.3 ms and eight-client p50/p95/p99 at 257.6/463.1/463.1 ms. All 30 samples in each run overlapped the deep check and backfill. Lookup-admission peaks were one and eight; host peaks were four in each run. The 500-commit publication transactions took 27,664 and 23,292 microseconds, growing the WAL file from 94,792 to 972,352 bytes; sampled WAL peak was 4,597,952 bytes. The completed graph stored 10,198 raw parent edges and zero transitive ancestor rows. Raw fact payloads occupied 1,580,735 bytes, raw parent edges 1,142,176 bytes, and the quota-counted unreferenced staging total was 2,586,700 bytes. Controlled deep-check and lookup-identity disconnects reaped their host processes in 203.9 and 226.2 ms respectively. A separate Git trace of the 10,000-commit linear case counted eight Git processes during initial cold admission and four per idle warm query, constant in history length. These runs meet the 250 ms warm-p95 target for one client and miss it under the eight-client burst.

After adding peer-disconnect cancellation, three repetitions of that merged/check run completed without connection resets and with warm p95 values of 225.8, 279.6, and 230.8 ms. One run exceeded the provisional 250 ms target; the remaining performance work must explain and reduce that tail rather than treating the earlier single run as sufficient.

Use `--exercise-restart --warm-samples 5` to stop the daemon after an incomplete raw-fact checkpoint and verify that the next daemon reaches 10,000 facts. Use `--exercise-rewrite --warm-samples 5` to rewrite HEAD after a checkpoint, verify that the old pinned job becomes obsolete, and verify that the new exact trail excludes the abandoned HEAD. In both exercises use `--commits 10000` so prefetch remains active long enough for the intervention. Separate runs reached a 64-fact checkpoint before restart and before rewrite; they finished at 10,000 and 9,999 facts respectively. The service-lifecycle behavior suite also verifies that a zero ceiling stores no speculative facts.

On Windows, 2026-09-25, the 10,000-commit fixture returned `not_ready` in 411.0 ms, published its requested trail in 468.5 ms, and reached 10,000 raw facts and their parent edges in the background in about 13.4 seconds after publication. All 30 warm native CLI samples overlapped active prefetch: p50 160.1 ms, p95 164.2 ms, p99 170.2 ms. Ten later idle samples had p95 168.0 ms. The SQLite database file was 4,857,856 bytes. The provisional 250 ms warm-p95 target passed in this isolated backfill run; broader concurrent workloads remain unmeasured.

A separate trace run counted eight Git processes during initial cold admission and four per idle warm query; the latter count is constant in commit count. Trace I/O raised warm p95 during prefetch to 212.2 ms (p50 205.4 ms, p99 268.2 ms). Its idle p95 was 219.1 ms, its total Git process count across the fixture was 648, and its database file was 4,857,856 bytes. The trace run reached the full 10,000-fact ceiling; traced and untraced timings should be compared separately.

The synthetic history has no annotations. The optional deep check measures one concurrent check. Host peaks under saturation and sustained multi-client contention beyond the eight-client burst remain unmeasured. WAL sizes are observed file lengths, not write amplification or bytes flushed to disk; the latency results are measurements on the recorded Windows machine, not guarantees for other machines.

After routing job state, repository registration, and parser inspections through the canonical writer, the same 10,000-commit merged fixture with a 500-commit requested trail, concurrent deep check, installed host and host tracing produced warm p50/p95/p99 of 114.8/124.4/125.6 ms. All 30 samples overlapped check and prefetch. Requested publication took 22,619 microseconds; WAL length grew from 94,792 to 972,352 bytes, with a sampled peak of 4,597,952 bytes. Host-process peak was four, and the completed graph still had 10,198 parent edges, zero closure rows and 2,586,700 quota-counted unreferenced staging bytes. This is a one-client run; the earlier eight-client burst remains the relevant saturation measurement.

## Context

See `proposal.md` and the four capability specs. The repository currently contains no Rust implementation. The service must work per user on Windows, macOS, and Linux, own a single SQLite database, and coordinate with the Python package's versioned extension host.

## Goals / Non-Goals

**Goals:**

- Keep one authoritative writer and one deterministic index for all clients.
- Reuse Git traversal, entry/effect models, and validation through Rust library crates.
- Make fast-forward work incremental and every invalid anchor recoverable by rebuild.
- Bound indexing and retained history without evicting protected recent commits.

**Non-Goals:**

- Expose SQLite as a client API.
- Persist DECAY or CANCEL as queryable entries.
- Preserve legacy pickle or graph storage.
- Embed CPython in the service or ship a PyO3 Python package in this change.

## Decisions

### Use a Rust workspace with an always-on backend

The workspace separates `zmem-core` for Git identities, ordering, annotation/effect models and validation; `zmem-store` for SQLite transactions, anchors, queries, and eviction; and `zmem-svc` for configuration, scheduling, local transport, process lifecycle, and extension-host orchestration. The daemon is the only SQLite writer.

### Use HEAD object IDs as ancestry-aware anchors

An anchor stores canonical repository identity, indexed HEAD OID, schema version, and extension-set hash. A matching ancestor enables an `anchor..HEAD` walk; a non-ancestor or identity mismatch deletes that repository's derived rows and replays current reachable history. Commit graph order, not timestamps, determines effect application.

### Apply journaled context actions without effect rows

The Python host returns the completed action journal generated by expander context calls. Rust validates each add-entry, add-relationship, decay, cancel, and diagnostic action before applying it. Parent-before-child expansion resolves decay and cancel actions only against earlier reachable entries. Entry mutations and anchor advancement share one transaction, preventing duplicate multiplication after crashes. The transport journal is not persisted as an effect ledger, so rewrites and extension changes require a repository rebuild rather than inverse operations.

### Use a single-writer SQLite schema

The database holds repositories, anchors, commits, entries, relationships, and diagnostics. Entries use `(repository_id, full_commit_oid, annotation_index)` identity, base/effective score, validity, type, content, scope, and committer time. Foreign keys cascade whole-commit eviction. Read requests go through the daemon so schema and writer coordination remain private.

### Bound work separately from deterministic application

At most `max_concurrency` commit expansion jobs run globally. Results are validated and applied in deterministic parent-before-child and annotation order. SQLite writes remain serialized in transactions even when parsing work is concurrent.

### Treat the retention limit as soft when protection wins

After successful writes, eviction selects the oldest eligible committer time and removes its complete commit cohort. The 14-day wall-clock protection is evaluated before capacity. If no eligible cohort remains, capacity may be exceeded until entries age out or protection is disabled.

### Invoke Python out of process

`zmem-svc` launches the compatible Python extension-host command and exchanges length-bounded JSON messages containing the host's typed action journal. It validates protocol versions, journal provenance/shape, identities, action kinds, scores, and references before persistence. Python expander classes never construct this wire representation directly. This retains language-neutral service ownership and avoids an embedded Python runtime.

## Risks / Trade-offs

- [Git timestamps may be future-dated or misleading] → Honor committer time as the accepted eviction contract and expose it in diagnostics.
- [No stored effect provenance prevents inverse updates] → Rebuild the repository on non-fast-forward history or extension identity changes.
- [Protected entries can exceed capacity] → Report over-capacity state and retry eviction when the protection window changes.
- [Extension hosts can hang or emit excessive data] → Enforce time, message-size, and process limits; leave the anchor unchanged on fatal expansion failure.
- [Cross-platform service managers differ] → Keep lifecycle adapters outside core/store crates and verify the public executable on each platform.

## Migration Plan

Create the database with an explicit schema version, register repositories afresh, and perform full initial indexes. Schema changes that cannot migrate safely rebuild derived entries from Git. Rollback stops the service and preserves or removes the cache file at user choice; Git repositories remain untouched.
